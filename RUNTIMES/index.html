    Runtimes

    A Micro-Agent definition is runtime-neutral. A runtime binds it to an agent framework behind the small AgentRuntime interface (SPI); the executable bootstrap selects one by name from a runtime registry. Nothing in the definition, core contracts or bootstrap depends on a particular framework.

     MicroAgentDefinition + MICRO_AGENT_* configuration
                  |
            bootstrap builds providers ──> RuntimeBuildContext
                  |
        RuntimeRegistry (name / alias / entry point)
                  |
   +--------------+---------------+------------------+
   |              |               |                  |
 custom       google-adk       langgraph        your runtime
 (reference)  (ADK adapter)    (StateGraph)     (entry point)

    Built-in runtimes

    Runtime Select with Extra Orchestration
    custom (aliases adk, reference) default none project-owned bounded model/tool loop in runtimes/custom
    google-adk MICRO_AGENT_RUNTIME=google-adk adk Google ADK LlmAgent and Runner in runtimes/google_adk
    langgraph MICRO_AGENT_RUNTIME=langgraph langgraph LangGraph StateGraph in runtimes/langgraph

    The custom loop lives in runtimes/custom. It was published as runtimes/adk, a misleading name (ADR 0008) that remains as a deprecated alias (AdkRuntime is CustomRuntime). runtimes/google_adk is the real ADK adapter.

    What each runtime supports

    This table is generated from what each runtime reports with every service configured (python tools/runtime_capabilities.py --write refreshes it, and a test fails if it is stale). Streaming and structured output also depend on the model provider.

    Capability custom google-adk langgraph
    Streaming native native native
    Structured output native native native
    Memory native native native
    MCP tools native native native
    A2A no no no
    Checkpoint / resume native native provided

    native means the framework or the reference loop supplies it; provided means the Micro-Agents governance layer supplies it because the framework does not; no means not available.

    Gaps filled by the governance layer: langgraph: checkpoint / resume.

    Gaps left open: a2a (custom, google-adk, langgraph).

    Uniform guarantees covered by conformance cases: 17 of 17.

    A2A is served by the HTTP interoperability layer for every runtime, so the runtime-level flag is no everywhere. Behavior beyond these flags (policy, audit, telemetry, argument validation, idempotent side effects, approvals, retry, fallback, circuit breaking, deadlines, usage accounting, session portability) is identical on all runtimes and proven by the conformance suite. The remaining differences are where state lives and which model path is native:

    Difference custom google-adk langgraph
    Approval continuations ApprovalStore ADK native, in the session ApprovalStore
    Native framework model path no yes (Gemini) no
    Checkpoint state neutral schema ADK-specific neutral schema

    langgraph shares the reference runtime's approval pause/resume (through the same ApprovalStore, including MICRO_AGENT_APPROVAL_ENDPOINT). Where it lacks a feature it fails closed: without a CheckpointStore, checkpoint_id requests are rejected.

    LangGraph has no checkpointing of its own here: the governance layer supplies it (provided). With a store configured, state is snapshotted at tool-round boundaries in the neutral, versioned schema and checkpoint_id resumes it, so a checkpoint written by the custom runtime can be resumed on LangGraph and vice versa. A checkpoint written by the Google ADK adapter carries ADK session events and is refused by the neutral runtimes (and the reverse). Models are reached through the Micro-Agent provider SPI, so every built-in provider (OpenAI-compatible, Azure OpenAI, Anthropic, Gemini, fake) works unchanged; no LangChain chat model is involved.

    Choosing one

    • Start with custom. It has no extra dependency and the fullest feature set.
    • Pick google-adk to reuse ADK agents, its session model or native Gemini.
    • Pick langgraph when your organisation standardises on LangGraph tooling (graph visualisation, LangSmith) or you intend to extend the graph.

    The same definition and the same providers run on all three; see the conformance suite.

    Native versus provided capabilities

    RuntimeCapabilities.sources() reports each capability as native, provided or none. provided means the Micro-Agents gap-filling layer supplies it on top of the framework (ADR 0022); no built-in runtime reports provided only for langgraph checkpointing. The behaviors every runtime must show identically are listed in micro_agent.runtime.guarantees.UNIFORM_GUARANTEES and proven by the conformance suite.

    The abstraction layer

    Three pieces, all in micro_agent.runtime:

    • AgentRuntime — the SPI: capabilities, create, start, invoke, optional stream, stop, shutdown, health_probes, close. No framework type crosses it.
    • RuntimeBuildContext — everything the bootstrap built for the definition: model provider, session/memory/operation/approval stores, knowledge, MCP manager, policy, audit sink, telemetry and tool registry.
    • RuntimeRegistration / RuntimeRegistry — a name, a factory (RuntimeBuildContext) -> AgentRuntime, aliases, and the few bootstrap-facing facts (native_model, approval_store, approval_note, and provides: the capabilities the governance layer supplies for this runtime).

    The bootstrap never mentions a framework. It resolves the registration, builds the context, calls the factory. Built-ins are registered in micro_agent/config/runtimes.py, the only place in micro_agent allowed to import runtimes.*; each factory imports its adapter lazily so selecting one runtime never needs another's dependency.

    Adding a runtime

    1. Implement AgentRuntime (subclass micro_agent.governance.GovernedRuntime to inherit the shared governance — policy, argument validation, idempotency, audit, telemetry, retries, deadlines — and replace only the orchestration, as the LangGraph adapter does; adapters never import each other, a rule enforced by tests/test_dependency_rules.py).
    2. Write a factory that maps RuntimeBuildContext onto your configuration.
    3. Register it, either in code:

    ```python from micro_agent.runtime import RuntimeRegistration, register_runtime

    register_runtime( RuntimeRegistration( name="my-runtime", factory=build_my_runtime, aliases=("mine",), approval_note="my-runtime does not map MICRO_AGENT_APPROVAL_ENDPOINT", ) ) ```

    or from a package, with no change to Micro-Agents:

    toml [project.entry-points."micro_agent.runtimes"] my-runtime = "my_package.runtime:REGISTRATION"

    An entry point may point at a RuntimeRegistration or at a zero-argument callable returning one. It is loaded only when selected. 4. Select it: MICRO_AGENT_RUNTIME=my-runtime.

    Report capabilities truthfully, keep framework types out of the public boundary, and reject (do not silently ignore) configuration you cannot honour.

    Opting an adapter into the gap-filling layer

    A definition must behave the same whichever framework runs it (ADR 0022). Adapters supply orchestration only; the layer in micro_agent.governance fills the rest at the boundaries Micro-Agents controls, never by reaching into framework internals. Pick the path that matches who owns the loop:

    You own the loop (like the reference loop and LangGraph's graph). Subclass GovernedRuntime and implement _invoke_inner. Then call, from your orchestration:

    • self._execute_tools(...) for a tool wave (policy, argument validation, idempotent operations, approvals, timeouts, audit, telemetry);
    • agent._internal["model_provider"].generate(...), which is a GovernedModelProvider (deadline, span, latency and usage telemetry, deltas);
    • _load_checkpoint / _save_checkpoint / _delete_checkpoint at tool-round boundaries, and _approval_needed / _save_pending_approval / _replay_pending_approval for pause and resume.

    Retry, fallback, circuit breaking and the deadline are applied around _invoke_inner for you.

    The framework owns the loop (like Google ADK). Compose the same pieces at your boundaries: give the framework GovernedTool-wrapped tools (or a ToolGovernor call inside your tool shim), bridge its model calls through GovernedModelProvider, run each invocation through InvocationGovernor.run with use_tool_scope / use_model_scope bound, and store sessions in the portable transcript layout. Anything the framework keeps natively (for example ADK's confirmation flow) must still satisfy the same conformance case.

    Either way:

    1. Declare what the layer fills in RuntimeRegistration.provides; the capability then reports as provided, not native.
    2. Add your factory to tests/test_runtime_conformance.py and tests/test_session_portability.py. Every guarantee in micro_agent.runtime.guarantees.UNIFORM_GUARANTEES must pass; a provided capability runs the same cases as a native one.
    3. Regenerate the table above with python tools/runtime_capabilities.py --write (add your runtime to its RUNTIMES tuple) so the documented gaps stay true.
    4. Keep the adapter's imports inside its coupling cap in tests/test_dependency_rules.py; adapters never import each other.

    Changing runtime with sessions in flight

    A stored session is the same for every runtime: role/content messages (user, assistant with optional tool_calls, and tool results) under the plain session id. The Google ADK adapter keeps its richer native events in the session metadata and reloads them losslessly while the transcript is unchanged; if another runtime appended, ADK rebuilds its events from the transcript. So changing MICRO_AGENT_RUNTIME between deployments needs no export or conversion step. Sessions that an earlier version stored in ADK's prefixed layout are moved to the portable layout the first time they are read. ADK-only protocol messages (confirmation requests) are not part of the portable transcript.

    Session ids are shared across agents in the same store, as they already were for the custom and LangGraph runtimes; use distinct ids per agent.

    Proving a runtime conforms

    tests/test_runtime_conformance.py runs one contract against every runtime: every item of the uniform-guarantee list (micro_agent.runtime.guarantees): capability matrix, identity without framework types, invocation, session replay, the tool loop, model failure, startup health, policy denial, argument validation, idempotent side effects, approval pause/resume, audit and telemetry, checkpoint/resume, model retry/fallback/circuit-breaker, the invocation deadline and token usage. A capability reported provided runs the same cases as a native one. tests/test_session_portability.py writes a session under every runtime and reads it under every other. A new runtime joins by adding one factory to those files.

    tests/test_dependency_rules.py keeps the layering honest: micro_agent never imports runtimes outside the composition root, optional frameworks are never imported unguarded, and each adapter's fan-out into the framework is capped.

    Installing

    python -m pip install -e ".[dev,adk]"        # Google ADK
python -m pip install -e ".[dev,langgraph]"  # LangGraph

    Both extras are pinned. Neither is in the base install, the container image or the default CI job.
